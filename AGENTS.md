## Working agreement

- Complete the requested work through validation and self-review. Resolve routine implementation
  choices from the code and state material assumptions; ask when missing information would change
  the intended behavior or scope. Continue independent work while awaiting an answer.
- Plans, audits, and reviews are read-only unless the user asks for edits. Preserve unrelated local
  changes. Apply existing authorization without asking again; a local edit does not by itself
  authorize a push, merge, tag, or publish.
- Read the files and applicable rules needed for the task. This file is the canonical repository
  guide; `CLAUDE.md` adds Claude-specific setup, and `.cursor/rules/` mirrors focused rules. Apply
  direct user instructions over repository workflow defaults, within system/developer constraints.
  If a rule blocks authorized work, cite the exact rule and explain the conflict.
- Treat memory, prior reviews, and model recommendations as context. Verify changing facts against
  current source, configuration, and the live PR head before relying on them. Keep durable project
  rules here rather than copying them into personal memory or another agent guide.
- Preserve the user's selected model and effort. Both are set and checked in the coding client; a
  model recommendation in these guides does not change that setting or prove a model performs
  better on this project.
- Use an independent reviewer for the cases required under "Pre-PR self-review" (T2) and for the
  reader rounds a PR's tier requires under "Reviewing PRs". Give each reviewer
  a bounded scope and reconcile their evidence. Other delegation follows the user's instructions
  and the coding client's rules.
- Report the outcome, checks actually run, and unresolved limitations concisely. For reviews, lead
  with actionable findings and exact file/line references. Distinguish a skipped check from a pass.

## What this is

Claudinho surfaces live football for the competition you follow (the World Cup, the Premier League, LALIGA, the Champions League and 12 more) in developer environments. Its surfaces:

- a **CLI** (`claudinho`): live scores and fixtures, **cumulative group standings** (from the provider's standings feed), a **knockout bracket**, a **fuzzy team resolver** for the World Cup roster (`claudinho team`: a nation name or code → FIFA code + flag + group), read-only **prediction-market signals** (Polymarket odds — informational only) and **shareable terminal snippets** (`claudinho share` — copy-pasteable match **and standings** cards);
- a **statusline** (Claude Code **and Cursor CLI** — `init claude`/`init cursor` one-step setup) and a **score-aware hook** (Claude Code `UserPromptSubmit`), with a structured twin of both for a program, `claudinho ambient --json`;
- an **MCP server** (also a **Cursor Marketplace plugin** + cursor.directory listing), with the same reads as tools (scores and fixtures, standings, the bracket, market signals, share snippets): `get_team` and `list_competitions` are its two **offline** tools (`openWorldHint:false`); agents use `get_team` (the World Cup's nations, whatever the competition; it knows no clubs) for the 3-letter code `get_market_signal` takes; in a club competition `get_next_fixture` and `get_share_snippet` take a club's name or code directly, resolved against that competition's roster (`get_market_signal`'s `team` argument is a 3-letter code, and real market data, Polymarket's, is read for the World Cup alone);
- a **Claude Code plugin** (the band above the prompt, score toasts and the prompt context, on `claudinho ambient --json`; a match pane, `/claudinho match`, on `claudinho match <id> --json`'s `rows`, its `lines` for an older CLI; the goal moments: what each toast says, the goal and full-time celebration with the mascot, the band's bold score, on the view's `lineParts`, `finished` and per-record `pinnedSide`, `names` and `lastGoal`; in the reader's language, on the view's `lang` and `words`, each ambient run (the band's, `/claudinho`'s) handed `--lang`, the match runs too once any view states `lang`; an opt-in team look (your team's colors, the team the band follows, in the desktop and mobile apps, drawn as a band, a pitch or a pixel-art stadium corner, whose scarf is a national team's flag colors, whose goal moment plays for either side of your team's match with the goal word in the reader's language on its scoreboard, and which stands at the bottom right or, by an option, the bottom left)). The "Layout" table names its files.

It answers for **sixteen supported competitions** (one table, `packages/core/src/supported.ts`), one per request, chosen by `--competition <alias>`, then `CLAUDINHO_COMPETITION`, then the user's saved choice (`claudinho follow <alias>`, a config file) on the CLI, and by the `competition` argument on every MCP tool but `get_team` with the same two fallbacks; with nothing chosen there is no competition, never a default; `list_competitions` (the other offline MCP tool) lists them with what each offers. **Planned:** a desktop **notifier**, a precomputed **AI pundit**, and a small edge **gateway** that polls a data feed once for everyone.

## Commands

- `pnpm install` — install deps
- `pnpm build` / `pnpm test` / `pnpm typecheck` / `pnpm lint` — across all packages (`lint` = Biome, no formatter; a warning fails it, `--error-on-warnings`)
- `pnpm -F @claudinho/core test` — operate on a single package
- `pnpm release:qa` — pre-tag surface renderer (see "Release readiness")
- `pnpm gen:readme-matrix` — after a build, rewrites the capability matrix in the root README and the CLI's README (between `<!-- competitions:start -->` and `<!-- competitions:end -->`) from the supported table; `packages/core/test/readme-matrix.test.ts` fails when a committed block differs
- `bash scripts/plugin-test.sh` — the Claude Code plugin's kit tests (`packages/plugin-tests`) against the plugin folder, under the `claude` on PATH (CI pins its version); `claude plugin validate packages/plugin` checks the plugin itself
- `bash scripts/plugin-demo.sh` — assembles the plugin's demo (`packages/plugin-demo` with the plugin's drawing modules from this checkout) into a folder it prints; loaded in a session of the desktop app (`--plugin-dir <folder>`, or `CLAUDE_CODE_PLUGIN_DIRS`), its `/demo` command shows the band, the pitch and each state of the stadium (idle, live, a goal by either side) for a team, with no match. It shows what the plugin draws, never the plugin's path from a real goal (its readings, its memory, its toast)
- `pnpm canary` — after a build, asks the REAL feed, for every row of the supported table, the six questions of `CANARY_QUESTIONS` that apply to it, through the adapter (`scripts/espn-canary.mjs`, whose header lists them and what each checks): `live`, `day`, `window` and `standings` of every row, `knockout` of the bundled competition alone, `discovery` of every other row. A refused request form or a payload the parsers cannot fully read is a red row; a row whose verdict is `blocked` or `unreachable` is neutral and reported as a warning, because the canary could not answer that whole question (a block also ends the run: the provider said stop); an outage inside a window whose other part broke an invariant leaves that row red, with the outage in its detail. It does not replace the parsers' own tests. `.github/workflows/espn-canary.yml` runs it daily; it is unbadged and gates nothing. A red "Ask the feed" step is the canary's own, and a red step before it is not: read the step's log. A table with a red row: that row's verdict and detail say what the canary found, which is not always a change of the feed (`checkStandings` marks zero rows `changed` for any shape other than `none`, even when a league returns a healthy empty list of tables between seasons). No table and the line that `packages/core/dist` was not found (exit 2): nothing was asked. Anything else, an error with or without a table before it (a table with no red row included): the script or the runner failed, which is not a finding about the feed. A request form added to the adapter must be asked there or listed as covered: `espn-canary.test.ts` fails when a `fetch*` method of `EspnAdapter.prototype` is neither a question's `method` nor a key of its `COVERED_ELSEWHERE` list (it compares names; it does not prove the runner calls the method).

**Bumping `@biomejs/biome`?** Nothing to do — `biome.json`'s `$schema` points at
`./node_modules/@biomejs/biome/configuration_schema.json`, so it follows the installed version.
Keep that local path: `packages/core/test/biome-schema.test.ts` rejects a pinned URL or a missing
bundled schema. Hand-edit `biome.json` when necessary; `biome migrate` reformats it to tabs.

## Validation scope

- **Prose and agent instructions only:** review the diff, check local links and stated contracts,
  run `git diff --check`, and run the [private-document boundary check](#private-document-boundary-check)
  below. No application build or live-feed QA is needed unless executable
  configuration, commands, package contents, or product behavior also change.
- **Code, dependencies, or executable configuration:** iterate with affected tests, then run
  `pnpm -r build && pnpm -r typecheck && pnpm -r test && pnpm lint` before declaring the change ready.
  `scripts/gate.sh` is the local form of that gate with CI's smokes and guards (one verdict per
  step, `--commit <message-file>` committing only when every step is ok, or, with
  `--allow-offline-audit`, when the audit alone was skipped offline (the commit line says so and
  the exit stays nonzero)); it does not run `pnpm release:qa`, does not fetch the live feed, and
  leaves CI's Node 22 floor, Windows and macOS jobs to the push. Read all three in
  `scripts/push-and-watch.sh`'s SHA report.
  Build first because CLI/MCP checks use core's generated output. Run the relevant CI smoke and
  packaging checks; MCP contract changes also require the
  [base/head `tools/list` comparison](CONTRIBUTING.md#comparing-mcp-tool-contracts) and
  `pnpm -F @claudinho/mcp smoke:stdio`.
- **User-facing behavior and releases:** also run `pnpm release:qa` after build and inspect the
  output. Keep the "Release readiness" and feature acceptance gates below; a skipped live-feed
  check is not verified behavior.
  The `verify-claudinho` skill (`.claude/skills/verify-claudinho/SKILL.md`) and its control CLI,
  `node scripts/verify.mjs`, are the offline inner loop: one surface of the built binary driven in
  an environment built from scratch, offline unless told otherwise, with the evidence of every
  child kept; the control CLI replaces neither CI's jobs nor the live pass, `pnpm release:qa`.
- **A change to what the Claude Code plugin draws** (a scene's drawing or its motion, the look's colors): also
  assemble the demo (`bash scripts/plugin-demo.sh`), load it in the desktop app and look at every state the change
  touches. The PR's checks carry a line "Seen in the app" naming the states seen and the app's version, or say why
  not; a render in a browser is not that look (the app has frozen animations a browser plays), and a skipped look is
  not a pass. The demo proves the drawing, not the plugin's path from a real goal: say which of the two was seen.
- Add tests for changed behavior and failure modes. Do not add tests that merely repeat prose or
  implementation details. Once required checks pass, rerun or broaden them only for a subsequent
  change, a failure, or an unresolved concern. After a push, verify CI on that exact SHA.

### Private-document boundary check

Run this from the repository root. It needs only Node and Git, prints the scan results, and exits
nonzero for a tracked private document or a reference to one. `scripts/private-doc-refs.mjs` only
exports helpers; running that file directly does not scan anything.

```bash
node --input-type=module <<'NODE'
import { execFileSync } from 'node:child_process';
import { scanTrackedFiles } from './scripts/private-doc-refs.mjs';
const trackedPrivateFiles = execFileSync('git', ['ls-files', '-z', '--', 'docs/'], { encoding: 'utf8' })
  .split('\0').filter(Boolean);
const result = scanTrackedFiles(process.cwd());
console.log(JSON.stringify({ ...result, trackedPrivateFiles }, null, 2));
if (result.leaks.length || trackedPrivateFiles.length) process.exitCode = 1;
NODE
```

`pnpm check:pack` also runs the reference scanner and dry-runs package creation. Use it after a
build for packaging validation; a pass without a build does not prove the required artifacts exist.

## Releasing

Releases ship via `.github/workflows/publish.yml` on a `v*` tag, using npm **trusted publishing** (OIDC), with **no
`NPM_TOKEN`**, for all three packages (`@claudinho/core` · `cli` · `mcp`), all published **with provenance**. The
workflow has four jobs (`build`, `publish`, `release`, `mcp-registry`), so the npm credential never shares a job with
the repository's code or its dependencies; `publish` runs in the GitHub environment `release` and waits for the
maintainer's approval. `guides/releasing.md` holds what each job does and the invariant of the two that hold the
credential, the release-day checklist in full, what each step below checks, the tag step's failure cases, the MCP
Registry record and the lessons: read it before a release and before changing the workflow.

**Release-day checklist** (the maintainer's; each step in full in `guides/releasing.md`): first, once, the `release`
environment's rules saved (the tag rule `v*`, a required reviewer); then, on each of the three packages on npm, the publisher that names no environment deleted and one naming `release` added
with direct `npm publish` allowed, no more than 2 days before that package's first successful publish through it (npm
expires a new publisher that no publish validated in 2 days; the guide's checklist step 2 has the cases); then the tag, the approval of
the `publish` job, and the four jobs watched. A tag pushed before the environment's rules are saved runs `publish` in an
unprotected `release`, with nothing asking for approval: what then happens, and the order of the repair, are the
guide's two cases.

To cut a release:

1. Bump the version in the **three** `package.json` files (`packages/{cli,mcp,core}/package.json`) and in
   `packages/mcp/server.json` (its `version` and its npm package pin; `packages/mcp/test/server.test.ts` fails if
   it drifts). The cli `--version` and MCP `serverInfo.version` are injected from package.json at build time.
2. `pnpm -r build && pnpm -r typecheck && pnpm -r test && pnpm lint` (CI re-runs these). **For any
   user-facing change, also run `pnpm release:qa`** and eyeball every surface against the live feed
   before tagging (see "Release readiness").
3. Commit, open the release PR and squash-merge it. Then tag the commit the merge made on `main`,
   never the release branch's own commit (the squash is a NEW commit, and a bare `git tag vX.Y.Z` tags `HEAD`).
   With `<n>` the release PR:

   ```bash
   git fetch origin +refs/heads/main:refs/remotes/origin/main &&
     sha=$(gh pr view <n> --json mergeCommit --jq .mergeCommit.oid) &&
     git merge-base --is-ancestor "$sha" refs/remotes/origin/main &&
     git tag vX.Y.Z "$sha" && git push origin refs/tags/vX.Y.Z:refs/tags/vX.Y.Z
   ```

   When the chain stops before `git tag`, nothing is tagged: check that `gh pr view <n> --json state` says
   `MERGED`, then run the block again. When `git tag` or the push fails, stop: this step never deletes or moves a
   tag on `origin`; read the tags as `guides/releasing.md` "When the tag step stops at `git tag` or the push"
   says, and do only what its case says. A failed run is retried on the same tag with "Re-run failed jobs". The
   build's artifact is kept 7 days: after them a re-run that does not include `build` fails at the download (in
   `publish` or `mcp-registry`), and "Re-run all jobs" rebuilds it. GitHub re-runs a run for 30 days after it first
   ran and at most 50 times; past either, this step has no retry and the maintainer decides.
4. Once all four jobs are green, update the maintainer's own machine and read each version back (the CLI, the
   plugin, every installed copy of the MCP server): none of it updates by default. The commands are in
   `guides/releasing.md`.

**Adding or changing an MCP tool:** every tool declares an `outputSchema` and returns
`structuredContent` (`packages/mcp/src/server.ts`). A **new** tool must be added to
`OUTPUT_SCHEMAS` *and* to `packages/mcp/test/output-schema.test.ts` (which parses each handler's
`data` — healthy **and** degraded — against its schema). The output schemas are **hand-mirrored**
from the `@claudinho/core` types and kept permissive (`.passthrough()` on nested objects); the
`.strict()` top-level guard test is the safety net that catches schema/handler drift, so keep it
green.

## Commit attribution (all agents)

This repo is worked on by multiple AI coding agents. Commits produced with one are
**co-authored by the agent and the model** that wrote them, so `git log` (and the GitHub
contributors view) shows which agent — and which model — did the work. Add a trailer in the
**last paragraph** of the commit message, and credit the same in the PR body:

```
Co-Authored-By: <Agent> (<Model>) <agent-no-reply-email>
```

Use the model **actually in use**, not a hardcoded one. Examples, one per agent (Claude Code
uses Anthropic's no-reply address; Cursor and Codex follow the same pattern with their own):

```
Co-Authored-By: Claude Code (<model's short name>) <noreply@anthropic.com>
Co-Authored-By: Cursor (Composer 2.5) <...>
Co-Authored-By: Codex (<actual GPT model>) <noreply@openai.com>
```

Read the model from the current session; never infer it from an example, an older commit, or a
global default that the session may override. Use this `<Agent> (<Model>)` form even when the
coding client suggests a different trailer.

**One spelling.** `git log` holds several spellings of this trailer from before this rule; the form
below is the one.

- The key is `Co-Authored-By`, with that capitalization.
- The model is its short display name, with no vendor prefix: `Claude Code (Opus 5.5)`, never
  `Claude Code (Claude Opus 5.5)` and never `Claude Opus 5.5` alone.
- Each agent adds one trailer line. A branch with commits by two agents carries two lines in the
  PR body.

```
Co-Authored-By: Claude Code (Opus 5.5) <noreply@anthropic.com>
```

## Reviewing PRs (all agents)

- For PR reviews, first verify the local checkout matches the PR head before running gates:
  `gh pr view <n> --json headRefOid,headRefName` and `git rev-parse HEAD`. If they differ,
  check out or fast-forward the PR branch before reviewing.
- Review-only tasks are read-only unless the user explicitly asks for fixes. Lead with findings,
  classify them P1/P2/P3, and include tight file/line references. If there are no findings, say
  that plainly and list the checks run plus any residual risk. A note (a finding outside the
  review's threat model, next bullet) is reported under Notes, never as a P1, P2 or P3. A note is
  not pending: it does not withhold a confirmation.
- Do not treat a previous review, memory, or local branch name as current truth. Re-check the PR
  SHA, merge state, and CI status at the end of the review.
- State the review's threat model in the PR description before the first round, and give it to every
  reviewer. (This is the review's model, not the product's security model in `SECURITY.md`.) The default model: the programs a change runs beside (the coding client that loads the plugin
  or the MCP server, the operating system, the user's shell) behave as they ship; they are not
  adversaries. A finding that needs another program to refuse, hold or delay one of the change's calls to
  its host, a reload or restart landing inside a window of milliseconds, or the system clock moving
  backwards between two runs is a note, not a blocker, unless it is reproduced on the real host as it ships
  (by a reviewer, the runner or the coordinator, who says how); then it is a finding. A finding a person reaches by using the product blocks as before: opening or closing a
  window, a slow disk, a missing or old binary, a changed setting, the network. The model narrows what
  blocks a review; it relaxes no rule in this file. The provider's data stays untrusted (the trust
  boundary), our own processes racing each other stay in scope (the refresher's lock, the throttle note),
  and a change may widen its model in its description. When fix rounds open a new case of the same kind
  twice, stop and ask whether that kind is in scope before writing another fix.
- **Review follows risk: every PR has a tier.** The PR description states the tier beside the threat
  model. A PR that spans tiers takes the highest. The maintainer may raise or lower a tier.
- **T0**: prose and agent instructions only ("Validation scope", first bullet); a test that reads only
  the guides' text (a structure guard such as `packages/core/test/claudinho-mode.test.ts`), changed
  together with that text; a dependency bump whose lockfile delta moves no shipped (runtime) dependency;
  a CI-action pin; text that is never public. Any other test change is T1 or higher. The coordinator
  reads CI per job on the head and reads the whole diff. There is no reader round and no runner round.
  Prose that states a legal, privacy or security claim (`SECURITY.md`, `PRIVACY.md`, the
  disclaimer, "Hard constraints") is T1, not T0.
- **T1**: product behaviour (code, tests, executable configuration, package contents) outside the T2
  areas, and a runtime dependency bump. The readers and the runner read it in one round. After the
  fixes, only the reader that raised a finding confirms its fix.
- **T2**: the trust boundary (`packages/core/src/trust/`, the provider adapters); the cache, the lock and
  the refresher; the release pipeline (`.github/workflows/publish.yml`, the tag step); a change to the
  MCP tool contract (`tools/list`); anything touching money, legal or a new external API (the
  independent pass "Pre-PR self-review" requires). It gets the full loop: every reader confirms the
  same head.
- **The cap: at most 3 rounds per PR, in any tier.** The first read is round 1. After round 3 the
  coordinator stops. The maintainer then decides: merge with the remaining P3 findings tracked, narrow
  the scope, or authorize more rounds.
- **A delta that is not a round.** In T0 and T1, the coordinator confirms a delta that changes prose
  alone or the PR body alone. In T2, the reader that raised the finding confirms that delta alone. Text
  that is never public gets no reader round in any tier.
- **The merge names a held SHA in every tier** (`--match-head-commit`). In T0 it is the head the
  coordinator read with CI green per job. In T1 and T2 it is the head the confirmations name.

## Conventions

- Shared domain types live in `@claudinho/core` — never duplicate them.
- Every data vendor implements the `ProviderAdapter` interface — keep providers swappable. An adapter **FETCHES**; it must not interpret. Turning a payload into a domain type happens in `packages/core/src/trust/` and nowhere else (`packages/core/src/trust/espn.ts` is the model), because feed strings reach terminals, share cards, and Claude's context via the hook. Cache readers call the **same** constructors: `packages/core/test/trust-parity.test.ts` tests parity. `ProviderAdapter` keeps its plain-array contract. Record-level refusal is local: malformed, duplicate, or truncated records are omitted while readable siblings remain usable and attributed to the provider. (One stated exception, in standings: a payload that holds tables nobody inspected, more children than the bound or a child that carries a `children` value other than an empty list, is refused whole, because no table in it can be shown to be the only one with its key. That is not a record being refused; see the table-key bullet below.) A transport/JSON failure, an unreadable envelope, or a non-empty provider list with no usable records reaches the domain's degraded fallback. Never turn one refused record into a batch-wide outage.
  Narration: guides/conventions/trust-boundary.md
- **Standings expected scope and static fallback compatibility are separate contracts.** `expectedStandingsGroups` says which tables must exist for a provider result to be complete; it never authorizes bundled teams. `standingsFallbackGroups` explicitly says which groups may use the bundled roster. The default World Cup adapter advertises A–L for both. A custom-competition adapter may declare its expected letters but leaves bundled fallback unset, so an outage or omitted expected table returns empty + degraded and can never inject World Cup teams. After a successful open-scope fetch, an absent group means "no such group" only when the provider's INVENTORY of tables is complete; when a table it sent did not become one, an all-tables read returns the tables that were read and says `incomplete` (when none was read it is degraded: there is nothing to qualify), and a key that was not read is degraded, not absent. An all-groups read uses one fallback verdict because `StandingsResult` cannot honestly represent mixed live and static provenance.
- **A table has a key, and the key comes from the raw name.** `GroupStandings.group` is the key a surface selects by: a group letter (`A`), a numbered group (`A1`), a group under a league (`A-B`), or `LEAGUE` for a league's one table; every table but a lettered group also carries the provider's `label`. `parseEspnStandings` derives the key from the RAW name, whole, by an anchored grammar (the sanitized label is a different string: `Group A` plus an invisible character sanitizes to "Group A"). It works in two passes: names first (which children are tables, which keys are claimed twice: such a key belongs to neither), then rows, for at most `MAX_GROUPS` tables whose slot is taken before the first row is parsed. Nothing is skipped: a child either becomes a table or makes the inventory incomplete, and a payload with tables nobody can inspect (more than `MAX_TABLE_CHILDREN` children, or a child that carries a `children` value other than an empty list; a child with no such key is the normal case) is refused whole. A table at the payload's root, beside the children, is not read: it makes the inventory incomplete. A competition written down as having no table (`none`) answers with its own document, a name and a season (`sealSeason`: a year) and no table list or table, and with no root key but the measured ones (`uid`, `id`, `name`, `abbreviation`, `season`, `seasons`, and `children` when it is an empty list): only that is an empty answer. The keys are an allowlist, so an error body that also carries a name and a season is not that document. A league's single table is authorised per competition (`STANDINGS_SHAPE`), never inferred from a payload having one child. Two facts stay apart: `partial` (rows missing from a table) and the inventory (a table missing from the result). And a table key is not a fixture's group: only a lettered group feeds the group map.
- **Text has ROLES, not one universal cleaner.** A human label is prose (no controls, no format characters, no emoji — bounded by display columns AND code points); an identifier is checked against an exact grammar; a timestamp is re-emitted canonically; a flag is **generated** from the nation, never read from a payload or a cache file.
  Narration: guides/conventions/trust-boundary.md
- **A rejection says which KIND it is.** `ParseResult` distinguishes `valid` / `definitive-none` / `malformed` / `ambiguous` / `unresolved`. For per-item market resolution, `valid`, `definitive-none` and `ambiguous` are stable conclusions and may be cached for a TTL; `malformed` and `unresolved` must not become definitive negative market results. A successfully fetched provider batch is different: share its readable prefix for the coalescing TTL even when a sibling row was malformed, because refetching identical bytes cannot heal that row and must not starve valid siblings.
- **Market completeness reaches the renderer.** `cachedMarketSignals` / `marketSignalsFor` return `{ signals, complete }`; default-on annotations, dedicated market commands/tools, share snippets, and JSON/structured output must retain that verdict. A complete empty batch may render "no signal". An incomplete batch renders an explicit unavailable/incomplete notice and carries `marketComplete:false` or `complete:false`; never collapse it to an empty `Map`.
- **A verdict becomes output in ONE place.** When a result says something about itself that changes what a reader may conclude ("not available for this competition" is not "none found"), it states it as a field, and every surface turns that field into a structured key and a sentence through core (`packages/core/src/verdict.ts`): `verdictExtras` for the key, `verdictNotice` for the sentence that REPLACES the body, `verdictQualifiers` for the sentences that QUALIFY it. A surface never forwards the field by hand at an emit site: Adding a verdict means adding it there and declaring its key in the MCP output schemas (`verdictOut`; `incompleteOut` for the standings tools; `partialOut` for `get_today`, `get_live`, `get_match`, `get_next_fixture`, `get_bracket`, `get_market_signal` and `get_share_snippet`; in `packages/mcp/src/server.ts`; the strict schema test refuses an undeclared top-level key). When a result states a replacement, its qualifiers are not printed. On a surface a cut can reach (a tool's text, a share card) every sentence that qualifies the body is printed BEFORE it, and nothing follows the body but the footer in the text the handler builds (leave MCP truncation notices to `boundText` and `toContent` in `packages/mcp/src/server.ts`). A result states `partial` only when its read SAID it was not whole (`fetchMeta`: `complete: false`), never when the adapter said nothing. Discovery is the one read that composes an account of its own: `getScheduleAhead` decides `degraded` and `complete` from its months, and a month that said nothing of itself is not whole there. Off the bundle exactly two answers of `next` carry discovery's `partial`, both only after a discovery that was not whole: the unknown-name answer, and the answer `teamAhead` builds (a fixture, or none); no other branch of `nextOffBundle` states it. `match <id>` states discovery's `partial` only when discovery did not hold the id (when it did, any `partial` on the result is its own refresh's). A read that states `partial` succeeded, so `partial` is not what makes a result `degraded`; one result can carry both; two of the cases, pinned by tests: an off-bundle `match` whose refresh was not whole and did not hold the id is `partial` (the refresh was) AND `degraded` (the record shown is the provider's earlier one; `off-bundle-reads.test.ts`), and a bundled market fixture (`marketFixtureForTeam`) whose knockout window was not whole and whose candidate, not finished, failed its own-day refresh is `partial` (the window was) AND `degraded` (the refresh failed; `partial-reads-paths.test.ts`; a finished candidate falls through to the team's next fixture, an answer that states either read's `partial` and is `degraded` only when the window itself failed); the count is believed only as a positive integer (anything else leaves `partial: {}`: the count is not known), and the one rule that turns a read's account into the verdict is `partialOfRead`. Every emit site of a result that can state one already passes that result through, and a result type that gains its first verdict is wired once, where it is emitted. A table's structured form, with its `partial` verdict, has one mapping too (`tableData` in `packages/core/src/standings.ts`). For the live read, and for a dated read that merged no bundled schedule (`skeleton` not set), on the bundle and off it, an empty body after a read that was not whole says nothing was READ, never that nothing exists; off the bundle, after a discovery that succeeded and was not whole, an empty `match <id>` says "none read" too (after a whole one it states `betweenEditions` where that verdict's conditions hold, as the off-bundle bullet below gives them, else the window searched; after a failed one the answer is `degraded`). An empty `next` whose result carries `partial` (off the bundle, one of the two answers named above; a result that states `rosterIncomplete`, `candidates` or a replacing verdict says that instead): off the bundle a NAMED team's says "none read"; on the bundle, and for a PINNED team off it (asked with no team argument and no `CLAUDINHO_TEAM`), it keeps "no upcoming fixture" under the `partial` sentence, because `nextNoneReadSentence` answers only a result that carries a `query`. Whether the pinned case should say "none read" as a named team's does is the maintainer's open question, not a rule. A day whose read merged the bundled schedule (`skeleton` set) and whose list is empty keeps the bundle's empty answer and any `partial`; `marketsNoneRead` asks no `skeleton`. `live` never shows a row its read did not serve. `packages/core/test/verdict.test.ts` guards this by vocabulary (a surface's code never spells `unsupported`, `noCompetition:`, `incomplete:`, `partial:`, `inapplicable:`, `unknownTeam:`, `rosterIncomplete:` or `betweenEditions:` outside the MCP schema, a verdict's sentence or i18n key, the horizon, window, "none read" or unserved sentence, a card's empty note or run cue, or a table's `partial` key); it catches a copy, not every way to write one, so the rule is still yours to keep. This sentence lists what the guide holds; it states none of those rules. Read it before changing what a result says about itself.

- **Off the bundled competition, `next`, `match <id>` and `bracket` answer from the competition itself.** `next <club>` resolves the query (a name or a code, as typed) with `resolveClub` against `rosterFor` (the standings, one read, `complete` only when a table was asked for and read whole with an id on every row) and the schedule ahead as positive evidence: one hit with an id resolves (one hit by CODE or by a FUZZY name only against a roster read whole, or where no table exists: a code is not an identity and a partial name may be another club's too; an exact name resolves anyway), two or more are `candidates` (never a pick), none is `unknownTeam` only against a complete roster and a whole read of the span; where a table was asked for and not read whole, a name that cannot be answered without it is `rosterIncomplete` (a verdict, not `degraded`: the provider answered). The end is the provider's STATED season end (`ended`: its calendar day), an administrative date, not the last match: A match found by its id is answered as asked, the previous final included (a historical question, like `today` on a date of the old edition). - **A window is composed of the requests the provider accepts.** `EspnAdapter.fetchWindow` asks a day at a time (up to three days) or a month at a time (longer; more than three months is refused unasked), sends the parts together, and settles every one before it answers, so a throttle that arrives after a sibling's quick failure has armed the cooldown. It returns ONE result with one account: any part's failure fails the window (a throttle wins: the one the adapter retains, whose deadline is latest counted from when each was received); a part whose ENVELOPE cannot be read is a failed part, whatever its siblings hold (the unreadable-envelope rule above is asked of each response); a part that filled the request's `limit` (the provider returns a silent chronological prefix) fails it too; a refused RECORD, or a fixture in two parts (compared before a month is narrowed to the window; the first copy counts), leaves it `complete: false` with the readable rest usable, and the "no readable record" rule is asked of the whole window, not of each part. An incomplete answer cannot prove a fixture is gone: a caller that keeps a previous answer (the refresher's knockout slice, and off the bundle its schedule slice) must not let it erase one. It keeps what the answer did not READ (`mentioned`: everything the answer read, also a tie it set aside as postponed or played). Both rules below are about an INCOMPLETE answer; a whole answer that is taken replaces either slice (`applyDiscovery` refuses any answer, whole or not, whose index would pass its bound: that is a failed discovery, and the slice stands). The knockout slice (`runRefresh`), when it holds a tie that is upcoming (`isUpcoming`: not postponed or cancelled, its kickoff not yet passed): with both seasons known and the same (by year) it keeps the upcoming ties the answer did not read; with both known and different the answer replaces the slice; with either unknown the slice stands as it was and the read counts as a failed attempt. A knockout slice that holds no upcoming tie takes any answer that did not fail. What the cycle then publishes is still one season per snapshot: a knockout slice whose season is known to differ from the live read's is dropped. The schedule slice (`applyDiscovery`) keeps the entries at stake (kickoff from six hours ago, `RELEVANT_BACK_MS`, through 16 days ahead, `SCHEDULE_HORIZON_MS`) that an incomplete answer did not read, unless the two seasons are known to DIFFER, because there an unknown season is an ordinary state (a discovery whose span touches two seasons states none); an incomplete answer known to be another season keeps none of them. Whatever an answer READ is taken from the answer: an entry it read and no longer returns inside the span is gone, whatever the seasons. The season the schedule slice then stores is a claim about every entry, so a union that KEPT entries stores the answer's season only when the two were already known to be the same, and none otherwise: a kept entry is never given a season it was not read under (an answer of "another" season could then delete it). The knockout-facing interactive reads (`next`, `bracket`, their share cards; CLI text and `--json`, MCP text and `data`) carry the window's `complete: false` as the `partial` verdict (see the verdict bullet), and so do `next` and `match <id>` off the bundle (`next` from discovery; `match <id>` from discovery when discovery did not hold the id, and from the match's own refresh alone when it did), and every other interactive read of fixtures: `today`, `live`, `match` on the bundle, the market surfaces (`markets <id>`, `markets next <team>` through `marketFixtureForTeam`, and `markets <date>`, which forwards the fixture read's verdict only where markets cover the competition, `marketsCoverCompetition`), and their MCP and share twins (see the verdict bullet for what each prints). The standings reads carry none of it: `getStandings` states a table's own `partial` and the inventory's `incomplete` (the table-key bullet). The statusline, the hook and the cache do not carry it: they are ambient and cache-only; the cache's live slice records completeness in `liveComplete` (whether the read that filled it was whole), which the statusline's syncing rule, `ambient --json`'s `current` and its `finished` list ask, and no other verdict. A three-day window cut at the provider's limit still THROWS (it is `degraded`, not `partial`): turning it into a returned partial would change what the refresher does with it. Full time is a match seen in play that a whole read returns finished, never a match that left the list. The guide holds this bullet whole: the account's `seasons` and `omitted`, the two season rules (the window's and discovery's), when two seasons fail a window and who asks across seasons, when a composed season keeps its dates (`agreedSeason`), the provider's day (`bucketDay`), and the refresher's record of play (`play`): how it advances, when an entry is dropped, and what reads it. The reader (`finishedFromCache`) looks at the record's first 64 finished entries (`MAX_PLAY`) and lists none whose stamp is invalid or ahead of the clock, whose record does not seal as finished with a score, whose match the live list holds, or whose id it has already listed. The plugin's full-time moment reads that list; the statusline's countdown and `ambient --json`'s `next` read only its ids (a match the record holds, in play or finished in its last 10 minutes, is never a due fixture's `now`; `playRecordIds`, once per render, without sealing a record); the hook reads none of it, and the hook's line gains `(FT)` for a finished record only.

- **A refresher decides under the lock, and a throttle always has somewhere to be written.** `runRefresh` takes a first look at the cache without the lock, and that look may only decide NOT to ask; a decision to ask the provider is made from the state read after `claimLock` (between the two, another refresher can have published a fresh slice or a backoff). A provider throttle (403/429) goes into the snapshot under that lock, and every writer then offers it to the scope's NOTE, whatever became of its publish, unless taking the lock itself threw (`claimLock` creates the cache directory first: where that cannot be made, a command's `persistBackoff` ends before the note is tried) (`backoffNotePath`: lock-free, atomic, never deleted, an expired one is just not believed; when `ensureBackoffVisible` answers false, this writer has not seen the note hold the deadline (a deadline this writer's own clock does not believe is not written; a write can fail; what was written may not read back to this process): a command keeps the deadline and tries again at a later chance (`persistIfNewer`), the refresher asks once in a cycle): the lock can be taken, the publish refused or its write failed (a publish that throws is one that did not happen), the snapshot unreadable, and a reader of another cache format rejects the snapshot whole, deadline included; it used to be dropped. A throttle counts as written only when the note holds it: after its attempt to publish, refused, failed or not, each writer (a command's `persistBackoff`, the refresher) asks `ensureBackoffVisible`, which writes the note unless the note already holds a deadline at least as late (`writeBackoffNote` reads the note back): one small write per throttle once it is held, never per cycle. Across a cache format bump the snapshot's deadline is read whatever the file's version (`backoffInEffect` with no state read), and a writer replacing a snapshot of another version notes that snapshot's believed deadline first (`writeState`). The backoff in effect is the later BELIEVED deadline of the snapshot's and the note's: every reader asks `backoffInEffect`, at the time it is then: the hot-path triggers (LAST, so the note is looked at only once a refresh would otherwise be started), the refresher when it decides, again before its second lane, and at publish, and a command arming its adapter. Every writer keeps the later believed one, comparing with `backoffInEffect` (the note included), never with the snapshot alone. `believedDeadline` is the one rule for a deadline: in the future and at most 30 minutes ahead; a value that is not believed neither beats nor hides a real one. A cycle whose base read is undefined (no snapshot of this scope and format could be read: none, unreadable, rejected) is paced by the scope's ATTEMPT RECORD (`attemptRecordPath`, beside the note, `{ at, count }`, never deleted, read only when no snapshot could be read), on every lane, the idle writers and the unknown-source publish included: under the lock and before anything else, a believed record that is not due returns (nothing written, nothing looked at), else the attempt is RECORDED (`admitAttempt`: the next count, `count + 1` up to the safe-integer ceiling, written and read back) and the cycle goes on with no look; only an attempt that could not be recorded asks the look, last, and the gate fails closed only where the look SEES that a publish could not heal (`admitNoBaseCycle`); in every other state the cycle goes on whether or not the attempt could be recorded. The lock API has one form: `holdsLock`, `releaseLock` and `publishState` take the token `claimLock` returned. A claim the claimer cannot read back is no claim (`claimLock` reads its token back; a lock nobody can read, in a cache directory whose new files nobody can read, admits no cycle: nothing asked, nothing published; the spawn per tick stays). Every file the CLI keeps (the snapshot, the note, the attempt record, the lock, the market cache, the run counter) is read through one descriptor, bounded and without waiting (`lookAtSmallFile`/`readSmallFile`, core's `files.ts`, re-exported by the CLI's `paths.ts`), and the user's config file through its no-follow form (`lookAtOwnFile`, under `readUserConfig`: `O_NOFOLLOW` at the open where the platform has it; on Windows, which has none, the entry is looked at, then opened, and the two must be one file, the same device and inode, else it is `symlink`), by the CLI and the MCP server alike; the only reads by path are the editors' settings file and standard input (the CLI), and none at all (the MCP server), pinned by each package's `cache-reads.test.ts`. A lock that vanished while a claimer looked at it is not removed (the claimer creates it once more); a stale one is taken over. Not closed, and stated in `claimLock`: two stealers of the same stale lock, and a lease lost while its owner still runs (the ownership check before a publish is not fencing). Not closed either, and stated in `writeBackoffNote`: the note's read-then-write is two steps, so two writers a few file operations apart can leave the earlier of two real deadlines. The guide holds this bullet whole: how the attempt record is settled and its pace, and the states of the snapshot's path a publish cannot heal, with the limit as it is. Read it before changing the lock, the note, the attempt record or a publish.

- **Off the bundled competition the refresher discovers, then polls only when a match can be in play.** There a cycle is now: DISCOVERY if due (`getScheduleAhead`: yesterday to 14 days ahead in provider days, each calendar month its own window, so two months that state two seasons are two answers, and the discovery states a season only when every month states the same one; the "no readable record" rule is asked of the whole discovery, not of each month: a month whose list held only records nobody could read read nothing, which leaves the answer incomplete while another month read something, and fails it when none did; once an hour, 5 minutes doubling to an hour while it fails, anchored on an attempt that is written BEFORE its request); the backoff again; the GATE on the slice as it now is; a live read if the gate is open and the live slice is at least 12 seconds old; then one final publish. A throttle is never a failed discovery, however short its wait, and every throttle gets the same five-minute floor before the provider is asked again, on both paths (`backoffToPublish`). The gate is open only for a discovered fixture that is on (not postponed, cancelled or finished) inside its 140 minutes, a match SEEN in play that no whole read has yet seen to be over (at most six hours past its kickoff), or one probe owed after a failed discovery. Every rule about the cache's `schedule` slice is a pure function in `packages/cli/src/scheduleSlice.ts`, and what is read back from the file is believed only within bounds (`scheduleView` is the one reader of everything in the slice but its display records: the index, both stamps, `failures`, `complete`, `inPlayUntil`, `probe`, the season; an index is whole or absent, never a prefix, an entry further ahead than discovery reads is not believed (`SCHEDULE_HORIZON_MS`), and its entries have one constructor in core's trust module; the display records are sealed where they are used, like every cached match; a republish carries the slice's completeness through `carriedIndex`, complete only while its index read back intact). `refreshWanted` is the ONE trigger for the statusline and the hook: never during a backoff, with a snapshot or without one, and never for a source nobody can ask once its idle snapshot exists. The statusline reads the slice's display records for a countdown and its gate (never the probe) for `live · syncing…`, and names no record that is postponed, cancelled or finished (`hasLiveWindow`, the index's own rule); `⚽ —` is the line for "nothing known". Detection is best effort and says so: it needs an invocation, a usable answer and no backoff. The knockout `fixtures` slice stays the bundle's, including after the cycle that rebuilds an older-format cache.

- **Bound the WORK, not just the output.** Collections are sliced before the per-record work, never after (`takeBounded`), and a surface reports `total`/`shown`/`truncated` from ONE `BoundedList` rather than recomputing counts per call site.

A card's notes come before its body, in this order: the verdict's `note` (on a table card, its tables-missing sentence; on a live or date card whose list a surface bounded, the list's cap after it, never in the title), then the card's own (a match card: the not-live note, then the market-incomplete note; a table card: the roster note, and each table's partial line between its title and its rows; a bracket card, in both styles: its structure-only or standings note), so a card pasted into a tool's text and cut from the end loses rows, never what qualifies them; nothing but the footer follows the body.
- **Star CTAs are human-interactive-only.** The npm→GitHub conversion nudges — `claudinho star`, the every-Nth dimmed footer on `today`/`live`/`next`/`table`/`bracket`/`match`/`team`, the post-`init` line, and the README callouts — live ONLY on interactive human surfaces. They are **never** on the hot path (statusline `prompt` / `hook`), **never** in `--json` or piped output (`process.stdout.isTTY`-gated, with a `CLAUDINHO_NO_STAR` opt-out), and **never** in MCP tool output/descriptions (that's agent context — a "star us" there wastes tokens and can leak to end users). The footer counter (`packages/cli/src/starNudge.ts`) is best-effort and never throws: a CTA must not break, slow, or pollute a command.

## Hard constraints (legal — do not violate)

- **Facts + emoji flags only.** Never add team crests, kits, player photos/likenesses, broadcast footage, or FIFA/Anthropic logos or wordmarks. The one exception: Anthropic's Claude mascot, drawn as three rows of text art in the Claude Code plugin's goal and full-time celebration only, in the engine's `claude` theme colour; it is removed if Anthropic asks. A team's colors, name and code, and a national team's flag colors as plain stripes, in the Claude Code plugin's opt-in team look and the scenes it draws from plain shapes (a pitch, a scarf, a stadium corner with fans, a goal and a scoreboard), are allowed. No crest and no logo is ever drawn.
- Keep the disclaimer, *"Not affiliated with FIFA, any confederation, league or club, or Anthropic."*, on user-facing surfaces. The Claude Code plugin's band and toasts omit the disclaimer and the provider's attribution as `prompt` and `hook` do (one-line ambient surfaces; `claudinho ambient --json` carries the disclaimer as `disclaimer` and the attribution as `attribution`); the plugin's `/claudinho` reply relays both from a view, and the `/claudinho match` reply leaves the attribution and the disclaimer to the pane it opened only when that pane opened on a surface that draws it and holds both (the pane draws both under the CLI's rows); otherwise it is the bare reply, relaying them as `/claudinho` does (each when the view carries it); its manifest, the marketplace entry and its README carry it. It is ONE constant, core's `DISCLAIMER` (`packages/core/src/disclaimer.ts`), which every runtime surface imports and never spells; a listing host's composition is `disclaimerLine(host)` (the constant with `, nor with <host>` before its period); the static copies (the listings, the public Markdown) are pinned to it by `packages/core/test/disclaimer.test.ts`, and the MCP Registry's 100-character card is the one stated exception (the fan line alone).
- The name stays cheap to change: add no new load-bearing use of `claudinho` beyond the ones there are (for example the binaries, the `CLAUDINHO_*` variables, the npm scope, the MCP server's name, the Registry, plugin and manifest names, the config and cache paths), and no logo or wordmark of Anthropic, FIFA, a confederation, league or club, or a listing host in the product's output or assets (the README's badges, which carry a platform's mark by that platform's own convention, are not the product). The one exception: Anthropic's Claude mascot, drawn as three rows of text art in the Claude Code plugin's goal and full-time celebration only, in the engine's `claude` theme colour; it is removed if Anthropic asks.
- Attribute data providers; respect their rate limits. `claudinho ambient --json` carries the attribution as `attribution` (when the snapshot names a provider and the line is neither the sign-off, `idle`, nor nothing known, `empty`; `degraded` does not decide), relayed by the plugin's `/claudinho` reply.

## Pre-PR self-review (run before declaring a change "done")

This is the lens an external reviewer uses — apply it yourself first. For a **T2** change
("Reviewing PRs": money, legal, a new external API and the other T2 areas), also run an
**independent adversarial pass** (e.g. a reviewer subagent with fresh eyes on the diff) and
self-classify any findings **P1/P2/P3**. Apply each item to the behavior and contracts affected by the change;
use "Validation scope" for the required checks.

1. **Verify external contracts against ground truth.** For any new API/integration,
   fetch a *real* response and confirm the parser **and the test fixtures** match it.
   Never ship against an assumed payload shape — green tests built on a wrong fixture
   prove nothing.
2. **Apply the change to *every* surface.** Enumerate them: CLI (text **and** `--json`),
   MCP (structured `data` **and** text), statusline/hook/`ambient --json`, share, and the READMEs. A behavior
   that lands on 3 of 4 surfaces is a bug — and "every surface" means each surface's *args*
   (tz/locale/flags) are threaded, not just that the surface exists.
3. **Audit the whole touched area against the Hard Constraints — including pre-existing
   code, not just the diff** (e.g. "attribute data providers" applies to *every*
   provider, not only the one you added).
4. **Adversarial failure-mode pass per new code path:** empty / missing / malformed
   input; transient vs. permanent error (never cache a transient failure as a real
   "no result"); duplicate / ambiguous data; timeout / deadline / concurrency. Default
   to **fail-closed**.
5. **State the worst-case latency/cost of any default-on path** under realistic load
   (e.g. "N sequential fetches × T timeout") and bound it (deadline + cache).
6. **Sync the meta in the same change:** READMEs, the Cursor rules (`.cursor/rules/`), MCP
   tool descriptions, and release guards (`publish.yml`, pinned tool versions). Flag any
   claim that went stale.

## Change discipline

**Changing a shared rule**

- **Put the rule where every path reaches it, then delete the other copy.** Live and
  cache paths must use the same rule.
- **Search for siblings before calling a class closed:** other timestamps, the hook
  beside the statusline, cache constructors beside provider constructors.

**Tests**

- **Make a new regression test fail before trusting it.** Temporarily revert the rule
  and confirm red, then restore it. Preserve unrelated edits.
- **Pin the CALL, not just the function.** For a call-site regression, temporarily remove
  the call and confirm red, then restore it.
- **Never assert wall-clock time.** Assert an observable consequence: put a valid item
  just past the cap and prove it is never reached.
- **Escape invisible characters in fixtures** so their meaning survives copying and review.

**Before saying it is done**

- **Run the checks required by "Validation scope" AND read the output.**
- **For a refactor affecting feed output, diff real-feed output against the base branch**,
  key order included. Report if the feed prevents verification.
- **Wait for CI on the SHA you pushed.** `gh run watch` on a queued run returns
  success; check `headSha` matches.

## Definition of Done (per user-facing feature, not per PR)

Before implementing a user-facing feature, write 3–5 acceptance criteria **from the
user's point of view**, plus an explicit statement of what the change does NOT cover.
Keep them in the PR description before the first commit; if no PR exists yet, draft that
description locally and use it when opening the PR. A feature spanning several PRs must
meet the same criteria across the whole feature. Verify them on a real terminal:

- The output is **unambiguous** to read (e.g. "which calendar day is this match?" across a 3-week span).
- Every entity renders **consistently with the rest of the product** (host nations show flags like every other team; no static/placeholder leaks; the resultless invariant holds).
- It behaves across **all timezones, all four locales** (en/es/pt/fr), and **every surface** (CLI text + `--json`, MCP `data` + text, share) — not just en/local/CLI.
- It **fails closed** (degraded feed → honest TBD/notice, never an invented or stale fact).

Scope these up front so the feature ships whole, not in dot-release pieces.

## Release readiness — run `scripts/release-qa.sh` before tagging

"Test it on a real terminal first" is executable: **`scripts/release-qa.sh`** (`pnpm release:qa`)
renders its CLI and share commands against the **live feed** (`bracket`: four locales, two
timezones), and ends with tripwires for known regression classes (bracket shows a calendar date,
`tz` is actually threaded, disclaimers intact; it SKIPs rather than fails on a degraded/unreachable
feed, so a network blip never blocks a release). Build, run it, **read the output**, then tag. It
does not replace the eyeball — its job is to put those renders in front of you so nothing ships
unseen. (It covers CLI/share rendering; MCP arg-threading is guarded by
`packages/mcp/test/tools.test.ts` — keep that green too.) It exports no competition: it FOLLOWS
the World Cup in a temporary config directory it creates and removes (`claudinho follow
world-cup`, as a user would: the mode line names no source), and `CLAUDINHO_COMPETITION=<alias|slug>
pnpm release:qa` renders another (the environment wins over the saved choice). Its header names
the competition the built CLI RESOLVED, read back from `--json`, never assumed. After that pass it renders a short CLUB pass: the Premier League followed in a second temporary
config directory, never the bracket, with `prompt` against a seeded cache and the refreshers it would start counted
(none); a between-editions league is a valid render, an outage is reported as one, and the club pass is skipped when
the header says the environment chose the competition. What it decides about the
competition (the bundle-drift tripwire runs only when the competition the built CLI RESOLVED is
the bundled one; an unresolved competition or an unreadable verdict FAILS, never SKIPs) lives in
`scripts/release-qa-lib.mjs`, tested offline by `packages/core/test/release-qa.test.ts`.

## Release cadence — batch, don't dot-release per fix

Two kinds of release, and only one is urgent:

- **Hotfix-now** — live data *correctness* only (a wrong score/standing *during* a match,
  or a feed outage rendering as authoritative). Ship immediately.
- **Everything else** — UX, polish, cosmetics, follow-on sub-features — **batch** onto the
  working branch and release as a single bump. Stack review fixes for the same feature into the
  same PR before merge.

Every release carries real toil (a multi-file version bump, the live pass, the maintainer's machine
updated). Fewer, fuller releases cut that directly. When unsure, accumulate.

## Don't

- Don't put API keys in client packages — keys live **only** in the gateway.
- Don't block the statusline hot path on the network — read from the local cache (<150ms).
- Don't cite anything under `docs/` from a tracked file (code comments, Cursor rules, templates, READMEs). That folder is maintainer-private and gitignored; a public reference leaks a private path and goes stale when the private tree changes. `scripts/check-pack.mjs` (run in CI) fails on any `docs/<name>` reference.
